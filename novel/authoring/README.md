# 인터랙티브 스토리 집필 형식 v1

연속성 관리 형식·경로별 생성 자료는 [../continuity/README.md](../continuity/README.md)를
참고한다. 확정 설정, 인물별 지식, 사건 기록과 장면 계약을 본문에 함께 연결한다.

게임용 이벤트 엔진이 아니라 **집필 원고와 편집 메타데이터**다. 게임 소스·진행 규칙을
바꾸지 않는다. 원작 사실, 각색, 새 창작을 구분하면서 선택·분기·합류를 작성한다.

- 형식: [story.schema.json](story.schema.json), JSON Schema 2020-12.
- 구조 예시: [drafts/prologue.json](drafts/prologue.json).
- 원문 보관소: [../../story_material/scripts.json](../../story_material/scripts.json).

예시는 **구조 초안**이다. 기존 프롤로그 산문 전체를 옮긴 완성 원고가 아니다.
원문 인용·영입 선택지·조건부 문단 몇 개와 미작성 표시를 넣었다. 감옥에 첫 의뢰 전에
접근 가능한지도 아직 검토 중이므로 선택 메뉴를 원작의 확정 경로로 읽으면 안 된다.

## 세 층을 분리한다

| 층 | 필드 | 역할 |
| --- | --- | --- |
| 원문 근거 | `source_refs`, `literal_ids`, `source_mapping` | 어느 파일·줄·문자열에서 가져왔는지 |
| 집필 장면 | `nodes`, `blocks`, `choices` | 읽는 본문, 선택지, 다음 장면, 분기·합류 |
| 이야기의 기억 | `state_definitions`, `when`, `effects` | 지식·동료·관계·사건·퀘스트 상태 |

추출 JSON은 재생성할 수 있는 원문 자료이고, `authoring/drafts/`는 사람이 집필하는
원고다. 원문 추출 도구는 이 폴더를 덮어쓰지 않는다. 퀘스트마다 별도 JSON을 쓰고,
원작의 한 지도가 아니라 하나의 집필 단위를 파일 경계로 삼는다.

## 원작과 창작의 표시

`provenance`는 장면·본문 블록·선택지·상태 정의·상태 변화에 각각 붙인다.
장면의 표시가 그 안의 모든 문장을 자동으로 원작으로 만들지는 않는다.

| `origin` | 의미 | 예 |
| --- | --- | --- |
| `source_exact` | 해당 텍스트가 원문 그대로 | 원문 대사 조각, 영입 수락·거절 문구 |
| `source_adaptation` | 원작 사실·사건을 집필용으로 표현 | 영입을 동료 명단 상태로 추상화, 원문을 재서술 |
| `authored` | 새로 만든 문장·선택·설정 | 이동 묘사, 내면, 신뢰도, 탐색 경로 메뉴 |

`source_refs`가 붙은 창작도 여전히 창작이다. 참고 근거를 밝혔다는 뜻이지 원문에
그 문장이나 시스템이 있었다는 뜻은 아니다. `source_exact` 상태 변화는 금지한다.
집필용 효과는 Pascal 연산 자체가 아니므로 `source_adaptation` 또는 `authored`다.

원문 출력은 조각별 `source_quote`로 보관하고 `literal_ids`에 원본 발생 ID 하나를
연결한다. 빈칸·오탈자·잘린 단어도 바꾸지 않는다. 읽기 편하게 이어 붙인 문장은 별도
`source_adaptation` 블록으로 작성한다. 원문 대체 표시와 감사를 거쳐 이중 출력은
나중에 프리뷰에서 조절한다. 현재는 프리뷰·게임 실행기를 만들지 않았다.
동적 이름·표현식의 완성 문구는 아직 지원하지 않으며 원문 추출 자료를 참고한다.

`speaker`는 집필용 화자 ID/표기이며 확정된 원작 이름이 아닐 수 있다. 원문에서
화자를 특정할 수 없으면 `null`을 유지하거나 표기가 편집 추정임을 `note`에 쓴다.

## 상태는 사건·지식·의견을 분리한다

| 범주 | 예 | 구분할 점 |
| --- | --- | --- |
| `knowledge` | 특공대원의 사연, 반대 증언을 들음 | 들었다는 것과 그것이 사실이라는 것은 다름 |
| `companions` | 선택 영입 명단 | 영입, 교체, 이탈, 사망을 같은 것으로 취급하지 않음 |
| `relationship` | 성주에 대한 신뢰 | 별도 창작이라면 원작 시스템으로 표시하지 않음 |
| `event` | 방문 여부, 특정 사건 경험 | 재방문·반복 장면 처리 |
| `quest` | 의뢰 수락·목표 달성·보고 | 원작 카운터와 대응 근거를 기록 |

자료형은 `boolean`, `integer`, `string`, `string_set`이다. `initial`은 새 이야기의
시작값이다. 퀘스트를 넘길 때는 초기화 대신 이전 상태를 전달한다. `scope: story`는
전편에 유지할 기억이고, `scope: quest`는 해당 파일 안에서만 쓸 상태다.
초기 동료와 영입 동료를 구분하고, 슬롯 제약·교체·사망은 별도 상태로 추가할 수 있다.
예시의 `companions.optional_recruits`는 전체 생존 일행을 의미하지 않는다.

원작 `party.etc` 바이트를 이 상태로 바꾸는 것이 아니다. `source_mapping`은 근거를
설명하는 메모이고 실행하지 않는다. 실제 게임 저장값과 집필 상태는 독립적이다.

## 장면과 선택의 연결

예시 흐름은 다음과 같다.

```text
도입 → 성 안의 선택 허브 ──→ 성주 접견(합류) → 첫 퀘스트 파일
                 ├→ 주점 ─────────┘
                 └→ 감옥: 영입 / 거절 ─┘
```

주점과 감옥을 다녀오면 허브로 돌아간다. 다른 곳을 추가 방문하거나 성주를 바로
만날 수 있다. `merge`는 상태를 지우는 곳이 아니다. 같은 장면 안에서 `when`에 따라
앞서 들은 이야기와 동료에 대한 문단이 추가된다.

| 필드 | 의미 |
| --- | --- |
| `node.kind` | `scene` 장면, `hub` 탐색, `branch` 선택, `merge` 합류, `boundary` 파일 경계, `ending` 이야기 종료 |
| `entry_when` | 장면 진입 조건. 충족하지 못하면 들어가지 않으며 자동 대체 경로는 없음 |
| `blocks` | 순서대로 읽는 본문. `author_note`는 집필 메모이므로 독자에게 출력하지 않음 |
| `block.when` | 그 문단만 표시할 조건 |
| `choice.when` | 선택지 표시 조건. 거짓이면 숨김; 비활성 표시와는 별도 |
| `choice.target` | 선택 후 이동할 같은 파일의 장면 ID |
| `choice.effects` | 선택을 확정할 때 순서대로 기록할 상태 변화 |
| `branch_kind` | 이동·문구·지식·동료·관계·퀘스트·엔딩 중 주된 영향 |
| `consequence` | 집필자에게 보여 줄 결과 설명. 본문 스포일러로 출력하지 않음 |
| `handoff` | 다음 퀘스트와 전달할 상태. `entry_node: null`은 아직 미연결 |

선택 조건은 **변경 전 상태**, 대상의 진입 조건과 본문 조건은 **효과 적용 후 상태**로
해석한다. 효과는 `set`, `increment`, 집합 `add/remove`를 사용한다. 같은 장면의 재진입
때는 조건을 다시 읽고, 단지 문단을 읽었다고 효과가 발생하지는 않는다. 사실을 들은
경험은 해당 장면을 마치는 선택에 명시적으로 기록한다. `string_set`은 중복을 허용하지
않고 `add/remove`는 이미 추가/제거된 값을 다시 처리해도 같은 결과가 되는 의미다.

조건은 `eq/ne`, 정수 비교 `gte/lte`, 집합 `contains/not_contains`와 `all/any/not`를
조합한다. 코드 문자열을 실행하지 않는다. 예:

```json
{"all": [
  {"state": "knowledge.missing_squad", "op": "eq", "value": true},
  {"state": "companions.optional_recruits", "op": "contains", "value": "mad_joe"}
]}
```

형식과 의미를 정한 것이지 엔진을 만든 것은 아니다. 수치의 상한·하한이나 자동 관계
변화는 없으며 필요하면 명시적 조건과 효과로 쓴다. 신뢰를 어떤 사건에 반영할지 쓰지
않은 상태에서 변수 이름만으로 후속 결과를 추정해서는 안 된다.

## 원문 누락 감사와 편집 상태

`meta.status`: `outline → draft → source_review → editorial_review → approved`.
`editorial`은 장면별 의도·작업 상태·근거·미작성 사항이다. `open_questions`에 접근
조건, 화자 추정, 동료 슬롯, 다음 파일 연결처럼 확정하지 못한 점을 남긴다.

`coverage.literal_dispositions`는 원문 문자열 발생마다 처리 결과를 기록한다.

- `verbatim`: 그대로 넣은 블록/선택지 ID. 실제 원문 일치 검사.
- `adapted`: 각색한 블록/선택지 ID. 원문 전문은 추출 자료에 유지.
- `alternate_path`: 공통 본문에서 빠져도 다른 선택 경로에 보존한 위치.
- `pending`: 아직 집필하지 않음.
- `non_story`: 코드용 문자열·파일명·UI 등. 제외 이유 필수. 대사를 임의로 이 분류에
  넣어 원문 누락을 숨기지 않도록 사람이 검토해야 함.

완료 범위는 **이 파일의 `source_refs`에 선언한 모든 줄 범위의 문자열**이다.
`required_source_refs`는 최소 근거 연결 검사이고 전문 보존 판정이 아니다.
`complete`라면 모든 범위의 발생 ID가 처리되어야 하고 `pending`·보류 근거가 없어야
한다. `approved`라면 미해결 질문도 없어야 한다. 형식상 완료는 전체 게임 대사나
해당 퀘스트 원문 범위 선정 자체가 완벽하다는 증거는 아니다. 검토할 때 추출 퀘스트
자료와 비교해 누락된 근거 범위도 추가해야 한다.

선택 경로끼리 충돌하는 대사는 한 경로에 모두 넣지 않는다. 모든 원문은 보관하되,
독자가 고른 경로에서 가능한 장면만 읽도록 대응시킨다. 경로별 원문·각색·창작 비율과
동료 후속 영향은 이후 편집 보고서로 확장할 수 있다.

## 검증

환경에 `jsonschema`가 필요하다. 설치된 환경에서는 다음으로 확인한다.

```bash
python3 tool/validate_story_authoring.py
PYTHONPATH=tool python3 -m unittest discover -s tool/tests -p test_story_authoring.py
```

검사: 스키마, ID 중복·존재, 원문 줄 범위·인용 일치, 상태 자료형·조건·효과,
퀘스트 간 전달 범위, 구조상 도달 불가 장면·종료로 나갈 길이 없는 장면, 원문 처리
목록, 미완성을 완료로 표시하는 오류.

**모든 조건 조합의 플레이 가능성은 검사하지 않는다.** 모든 선택지가 조건상 숨는
경우, 효과 이후 대상 장면 진입이 막히는 경우, 동료 슬롯 충돌, 후속 퀘스트에서
상태가 실제 쓰이는지는 별도 경로 시뮬레이션·사람의 검토가 필요하다. 검증 결과에
`condition_paths_verified: false`를 명시한다. 게임 빌드·런타임 연결은 하지 않는다.
